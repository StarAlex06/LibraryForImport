# Оценка производительности

## 1. Цель эксперимента

Цель эксперимента — оценить производительность библиотеки `table-importer` при импорте больших табличных наборов данных из трёх источников:

- CSV;
- XLSX;
- SQLite.

Для каждого формата измеряются:

- время выполнения полного импорта;
- пиковый объём выделенной памяти, отслеживаемой `tracemalloc`;
- количество импортированных строк;
- соответствие фактического количества строк ожидаемому.

## 2. Условия проведения

Тестовые наборы данных генерируются скриптом `scripts/generate_test_data.py`. Используются два размера наборов данных: 100 000 и 500 000 строк.

Для всех форматов размер чанка установлен равным 10 000 строк. Измерения выполняются скриптом `scripts/benchmark_import.py`.

Используются синтетические данные, сгенерированные одним скриптом. Это позволяет сравнивать результаты на наборах одинакового размера и с одинаковой структурой столбцов.

## 3. Результаты

### 3.1. Набор данных из 100 000 строк

| Формат | Время импорта, с | Пиковая отслеживаемая память, MiB | Число строк |
|---|---:|---:|---:|
| CSV | 0,23 | 11,57 | 100 000 |
| XLSX | 82,83 | 29,30 | 100 000 |
| SQLite | 0,78 | 25,20 | 100 000 |

### 3.2. Набор данных из 500 000 строк

| Формат | Время импорта, с | Пиковая отслеживаемая память, MiB | Число строк |
|---|---:|---:|---:|
| CSV | 1,00 | 57,71 | 500 000 |
| XLSX | 433,17 | 140,69 | 500 000 |
| SQLite | 3,77 | 125,36 | 500 000 |

## 4. Анализ результатов

### 4.1. Время выполнения

В обоих экспериментах быстрее всего импортировались данные из CSV. Импорт 500 000 строк занял 1,00 секунды. Для SQLite аналогичная операция заняла 3,77 секунды.

Наиболее медленным оказался формат XLSX: импорт 500 000 строк занял 433,17 секунды, то есть около 7 минут 13 секунд.

Таким образом, в проведённых экспериментах XLSX оказался наиболее затратным форматом по времени. Это может быть связано как с особенностями обработки файлов Excel, так и с реализацией источника данных и используемых библиотек. Для определения конкретной причины необходим отдельный профилировочный эксперимент.

### 4.2. Использование памяти

При увеличении объёма данных с 100 000 до 500 000 строк пиковая отслеживаемая память увеличилась для всех форматов.

На наборе из 500 000 строк наименьшее значение наблюдалось для CSV — 57,71 MiB. Для SQLite значение составило 125,36 MiB, для XLSX — 140,69 MiB.

Следует учитывать, что `tracemalloc` измеряет выделения памяти, отслеживаемые Python, и не обязательно отражает полное потребление памяти процессом. В частности, выделения в нативном коде сторонних библиотек могут учитываться не полностью.

### 4.3. Корректность импорта

Во всех шести проверках фактическое количество импортированных строк совпало с ожидаемым.

Это подтверждает корректность количества строк на использованных тестовых наборах. Однако одной проверки количества недостаточно, чтобы доказать полное совпадение значений, типов данных и обработки пропусков. Эти свойства должны дополнительно проверяться функциональными тестами.

## 5. Ограничения эксперимента

Результаты зависят от характеристик компьютера, версии Python, версий библиотек, структуры данных, размера чанка и реализации источников данных.

Для каждого сочетания формата и размера набора выполнен один измеренный запуск. Повторные измерения, медианные значения и оценка разброса результатов не проводились.

Пиковая память измерялась с помощью `tracemalloc`, поэтому эти значения нельзя трактовать как полное потребление оперативной памяти процессом.

Несмотря на чтение данных чанками, текущая реализация `ImportSession` сохраняет прочитанные чанки в памяти и объединяет их в итоговый `pandas.DataFrame`. Следовательно, чтение чанками само по себе не гарантирует ограниченного общего потребления памяти при импорте большого файла.

## 6. Выводы

Эксперимент показал, что библиотека успешно импортирует тестовые наборы размером до 500 000 строк из CSV, XLSX и SQLite, возвращая ожидаемое количество строк.

В проведённых измерениях CSV продемонстрировал наилучшее сочетание скорости и отслеживаемого потребления памяти. SQLite также показал небольшое время импорта. XLSX оказался наиболее медленным форматом и представляет основной кандидат для дальнейшей оптимизации.

Полученные значения следует рассматривать как исходную точку для будущих сравнений и оптимизаций, а не как универсальные показатели производительности библиотеки.
